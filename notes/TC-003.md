# TC-003 — The reply happened first

**Tracked revision:** `2026-09-25.1` (25 September 2026)  
**Problem:** distributed event order  
**Canonical page:** <https://tntresearch.co.uk/temporal-club/notes/003-the-reply-happened-first.html>  
**Case data:** [tc-003.json](../cases/tc-003.json)

Service A's clock reads `12:00:02.000` when it sends request R. Service B's clock reads `12:00:01.000` when it receives R, and `12:00:01.400` when it replies. A receives that reply at `12:00:02.500` on A's clock. These are local wall-clock readings, not comparable instants with a shared date or UTC offset.

Message relationships support `a_send → b_receive` and `b_reply → a_receive`. B's local event order supports `b_receive → b_reply`. Together they justify the causal sequence `a_send → b_receive → b_reply → a_receive`, even though sorting the clock strings would put B's events first. An unrelated event C on a third service cannot be placed in that sequence from these records alone.

Each pair in the [case data](../cases/tc-003.json) is a directed happens-before edge, not an unordered association. The challenge is to add a retry, duplicate, clock correction, or correlation failure that invalidates an assumed edge—or to add evidence that genuinely places event C.
